================================================================================
                 LOGIBOX ESP32 SETUP INSTRUCTIONS
================================================================================

This guide explains how to set up the LogiBox delivery vault hardware:

  - ESP32 #1: Keypad + LCD (OTP Verification + Camera Trigger)
  - ESP32-CAM: Snapshot camera (delivery evidence)
  - Optional: Reed switches (door detection) + IR sensors (parcel detection)

There is no separate door-controller board. The keypad ESP32 verifies the OTP
and starts/stops the ESP32-CAM so it captures delivery-evidence frames.


================================================================================
                         HARDWARE REQUIRED
================================================================================

CURRENTLY WORKING:
  [x] ESP32 DevKit (38-pin, CP2102)
  [x] 4x4 Keypad
  [x] I2C LCD (16x2, address 0x27)
  [x] AI-Thinker ESP32-CAM (OV2640)
  [x] USB-TTL adapter (FTDI/CP2102/CH340) for flashing the camera
  [x] Jumper wires
  [x] USB cable (for keypad ESP32)
  [x] 3x Reed switches (one per vault door)
  [x] 3x IR obstacle sensors (LM393, one per vault compartment)

WORKING (JUST WIRED):
  [x] 3x Reed switches (one per vault door)
  [x] 3x IR obstacle sensors (LM393, one per vault compartment)
  [x] 4-channel relay module (5V coils, opto-isolated)
  [x] 3x 12V solenoid locks (one per vault door)
  [x] External 12V/10A power supply for the solenoids

CASH POD (additive, independent of the door locks):
  [ ] PCA9685 16ch PWM servo driver (I2C, default addr 0x40)
  [ ] 3x MG996R servo (one per vault cash pod)
  [x] External 12V/10A power supply + buck converter set to 6V
  [ ] 2200uF electrolytic capacitor (servo rail)


================================================================================
                       PART 1: KEYPAD ESP32 (ESP32 #1)
================================================================================

WIRING (ESP32 38-pin DevKit, CP2102)
------------------------------------
  Keypad Row 1  -> GPIO 4
  Keypad Row 2  -> GPIO 5
  Keypad Row 3  -> GPIO 14
  Keypad Row 4  -> GPIO 13
  Keypad Col 1  -> GPIO 15
  Keypad Col 2  -> GPIO 16
  Keypad Col 3  -> GPIO 17
  Keypad Col 4  -> GPIO 18
  LCD (I2C)     -> SDA GPIO 21, SCL GPIO 22, 5V, GND  (address 0x27)

  Reed Switches (when ready to wire):
    Reed V1     -> GPIO 33  (other leg to GND)
    Reed V2     -> GPIO 19  (other leg to GND)
    Reed V3     -> GPIO 27  (other leg to GND)
    Note: Uses internal INPUT_PULLUP. Closed door = LOW, open door = HIGH.

  IR Sensors (when ready to wire):
    IR V1 OUT   -> GPIO 34
    IR V2 OUT   -> GPIO 35
    IR V3 OUT   -> GPIO 36
    IR VCC      -> 3.3V (NOT 5V - GPIO 34-36 are 3.3V only!)
    IR GND      -> GND
    Note: LM393 push-pull output. Parcel present = LOW, empty = HIGH.

  Relay Module - control side (low voltage):
    Relay IN1   -> GPIO 32  (Vault 1 lock)
    Relay IN2   -> GPIO 25  (Vault 2 lock)
    Relay IN3   -> GPIO 26  (Vault 3 lock)
    Relay VCC   -> ESP32 5V/VIN pin (powers relay coils; NOT the 3.3V pin)
    Relay GND   -> ESP32 GND
    Note: The firmware drives relays active-LOW (GPIO LOW = energized).
    This is fail-secure at boot: ESP32 pins float high during reset, so
    all locks stay engaged until the firmware explicitly releases one.

  Note: GPIO 6/7 are the ESP32-WROOM-32 internal flash pins and are NOT used.
  GPIO 1/3 (USB serial to CP2102) and GPIO 34-39 (input-only) are also avoided.

CODE CONFIG (config.h)
----------------------
  - DEVICE_ID: must match a device doc in Firestore, e.g. devices/esp32-test-001
  - FUNCTION_URL: your deployed /api/device-verify-otp endpoint
  - ENABLE_REED_SWITCHES: set to 1 when reed switches are wired
  - ENABLE_IR_SENSORS: set to 1 when IR sensors are wired
  - WiFi credentials are NOT in the code. They are set once per device via
    the WiFiManager portal (see "WIFI & NETWORK SETUP" below).

UPLOAD
------
  1. Install the CP210x USB driver (silabs.com) so the board shows up as a COM port.
  2. Open LogiBox_OTP_Vault.ino in Arduino IDE
  3. Board: ESP32 Dev Module
     - Upload Speed: 115200
  4. Install libraries:
     - Keypad (Mark Stanley)
     - LiquidCrystal I2C (Frank de Brabander)
     - ArduinoJson (Benoit Blanchon)
     - WiFiManager (tablatronix)
     - Adafruit PWM Servo Driver (Adafruit) - required for the cash pod,
       installed even if ENABLE_SERVO_LOCKS=0 (the include is unconditional)
  5. Select the COM port for your CP2102 board and upload.
     If the upload fails to connect, hold the BOOT button, press RESET,
     keep BOOT held until the upload starts, then release.
  6. Open Serial Monitor @ 115200


================================================================================
                       PART 2: ESP32-CAM (SNAPSHOT CAMERA)
================================================================================

The ESP32-CAM has no USB port, so you flash it through a USB-TTL adapter:

WIRING (USB-TTL <-> ESP32-CAM)
-------------------------------
  USB-TTL 3.3V  -> ESP32-CAM 3.3V
  USB-TTL GND   -> ESP32-CAM GND
  USB-TTL TX    -> ESP32-CAM GPIO3 (RX)
  USB-TTL RX    -> ESP32-CAM GPIO1 (TX)
  USB-TTL DTR/3.3V -> GPIO0 (hold to GND while powering to enter flash mode)

FLASHING
--------
  1. Connect GPIO0 to GND, then plug in / power the ESP32-CAM
  2. Open LogiBox_ESP32CAM.ino in Arduino IDE
  3. Board: AI-Thinker ESP32-CAM
     - PSRAM: Enabled
     - Flash: 4MB
     - Partition: Huge APP
     - Flash Mode: QIO
  4. Install libraries: esp32-camera (espressif), WiFiManager (tablatronix)
  5. Select the USB-TTL serial port and upload
  6. Remove the GPIO0-to-GND jumper and press the reset button
  7. Open Serial Monitor @ 115200 and note the assigned IP + mDNS hostname

CODE CONFIG (LogiBox_ESP32CAM.ino)
----------------------------------
  - DEVICE_ID: devices/esp32-cam-001 in Firestore (ownerUid must be set)
  - FUNCTION_URL: your deployed /api/camera-upload endpoint
  - MDNS_HOSTNAME: "logiboxcam" (the keypad resolves this to find the camera)
  - WiFi credentials are NOT in the code - set them via the portal
    (see "WIFI & NETWORK SETUP" below).

CAMERA COMMANDS (LAN HTTP)
--------------------------
  http://logiboxcam.local/start          -> begin capturing every 3 seconds
  http://logiboxcam.local/start?vault=2  -> begin capturing, tag session "vault 2"
  http://logiboxcam.local/stop           -> stop capturing
  (or use the camera's assigned IP printed in Serial after boot)

The keypad calls these automatically when a delivery session starts/stops.


================================================================================
                        PART 3: SOLENOID LOCKS (12V + RELAY)
================================================================================

Each vault door is held by a 12V solenoid lock switched through one relay
channel of a 4-channel module.

WIRING (power side, per channel - keep 12V wiring separate from ESP32)
------------------------------------------------------------------------
  12V PSU (+)   -> Relay COM terminal
  Relay NO      -> Solenoid (+)
  Solenoid (-)  -> 12V PSU (-)

  Channel -> Vault mapping (matches the control-side pins):
    IN1 = Vault 1, IN2 = Vault 2, IN3 = Vault 3, IN4 = spare

  Use the NO (Normally Open) terminals: when the relay coil is off, the
  circuit is broken, so the solenoid stays locked.

  GROUNDING (two separate sides - get this right or the ESP32 will reset):
    Control side (opto-isolated):  Relay VCC -> ESP32 5V/VIN, Relay GND ->
      ESP32 GND. Relay IN1/2/3 -> GPIO 32/25/26. These MUST share a common
      ground with the ESP32 - the optocoupler on the board needs a return
      path to drive the relay coil.
    Load side (12V high power): 12V PSU, relay COM/NO and the solenoids
      form their own isolated circuit. The 12V PSU negative does NOT connect
      back to the ESP32 ground - the only link between the two sides is
      through the relay contacts and the optocouplers on the module.
    Sharing grounds across the two sides (e.g. tying the 12V PSU negative to
    the ESP32, or powering the module's LED indicators from the 12V rail)
    risks noise, resets and possible latch-ups. Keep the 12V wiring and the
    ESP32 logic wiring as two separate ground domains joined only inside the
    relay module.

HOW IT WORKS
------------
  1. Correct OTP for vault N -> relay N energizes -> solenoid releases.
  2. LCD shows "Vault N unlocked / Pull door open".
  3. User pulls the door open (reed switch sees OPEN), takes/leaves parcel,
     closes the door again.
  4. When the reed switch reports CLOSED, the solenoid re-engages and the
     keypad returns to the Select Vault screen.

FAILSAFES
---------
  - If the door never opens OR stays open, the lock force-re-engages after
    UNLOCK_MAX_TIMEOUT_MS (30s, config.h).
  - Power loss, WiFi loss, crash or watchdog reset => relays drop => locked.
  - Wrong OTP or rate-limited OTP never actuates any lock.

BENCH-TEST FIRST
---------------
  Wire only the control side (relays + ESP32), flash the firmware, run
  TEST 6 below, and watch the relay onboard LEDs before connecting the
  actual solenoids.


===============================================================================
            PART 4: CASH POD SERVOS (PCA9685 + MG996R, TRAPDOOR)
===============================================================================

Each vault also has a cash-drop trapdoor (a sliding metal sheet) controlled
by an MG996R servo on a PCA9685 16ch PWM driver. This is INDEPENDENT of the
solenoid locks - the door locks and the cash pod never share control pins.

The pod fires ONLY when a delivery is fully confirmed (door opened, parcel
placed, door closed = the 'door_closed_locked' event). At that moment the
servo pulls the metal sheet UP, releasing the cash pod. The pod then auto
re-locks after SERVO_POD_OPEN_MS (default 10s, config.h).

The pod NEVER fires on wrong OTP, 'no_parcel' aborts, or 'auto_locked'
failsafe timeouts - cash is only ever released on a verified delivery.

WIRING
------
  Power rail (CRITICAL - keep separate from the ESP32 logic side):
    12V PSU        -> Buck converter input (the same 12V supply as the
                      solenoids, or a second one - both share common GND)
    Buck OUTPUT    -> set to 6V (MG996R likes 4.8-6.6V; 6V = best torque)
    6V (+V)        -> MG996R red wires (all three) - STRAIGHT from the buck.
                      Do NOT rely on the PCA9685 header power rows for this.
    6V (+V)        -> PCA9685 V+ terminal (optional; on this board the V+
                      screw does NOT reach the header rows, so it does
                      nothing for the servos - feed it or leave it out)
    GND            -> PCA9685 GND, all three servo black wires, buck GND,
                      AND ESP32 GND  <-- COMMON GROUND IS MANDATORY
    2200uF cap     -> across the 6V rail, near the servos (smooths the
                      inrush when a servo starts; prevents brown-outs)

  IMPORTANT - POWER FLOW (verified on this build's board):
    The PCA9685 servo driver only provides SIGNAL to the servos. Its header
    power rows (V+) are NOT connected to the V+ screw / rail on this board
    (clone-board defect - every header pin reads only ~0.2V regardless of
    the rail). So the MG996R power pins MUST be wired directly from the
    buck converter, and ONLY the signal wire goes to the driver header.

  I2C control side (shares the LCD bus):
    PCA9685 VCC    -> ESP32 5V (VIN)   (logic supply - separate from V+)
    PCA9685 SDA    -> GPIO 21          (same bus as LCD SDA)
    PCA9685 SCL    -> GPIO 22          (same bus as LCD SCL)
    PCA9685 GND    -> ESP32 GND
    PCA9685 OE     -> GND              (always enabled; tie low)
    PCA9685 A0-A5  -> leave floating   (address stays 0x40; LCD is 0x27 - no conflict)

  Servo signal (MG996R yellow/orange wire into the header TOP pin only):
    Channel 3  -> Vault 1 pod   (board label "4" if the board is 1-indexed)
    Channel 11 -> Vault 2 pod   (board label "12")
    Channel 15 -> Vault 3 pod   (board label "16")
    NOTE: PCA9685 software channels are 0-15. If your board's silkscreen
    labels the headers 1-16, subtract 1 to get the software channel
    (label "4" = ch 3, "12" = ch 11, "16" = ch 15).
    NOTE: servo red/brown wires do NOT plug into the header - red joins the
    6V rail, brown joins common GND; only orange/yellow goes to the header.

  Servo current: MG996R stalls around ~2.5A on 6V. Three servos worst-case
  approach 7.5A - your 12V/10A supply handles it, but the buck converter
  must be rated for it too (>=3A continuous, 10A preferred). Use 18-20 AWG
  for the servo rail wires.

HOW IT WORKS
------------
  1. Correct OTP -> solenoid door lock releases (unchanged behaviour).
  2. Rider opens door, places parcel, closes door.
  3. Door closes + parcel confirmed -> solenoid re-engages AND the cash pod
     servo for that vault slowly pulls the metal sheet UP over ~2.6s
     (SERVO_RAMP_US_PER_SEC, configurable - a wire/pulley-like motion instead
     of a snap). The LCD holds "Releasing cash! / Vault N" for
     CASH_DROP_MSG_MS (4s, config.h) before returning to Select Vault -
     pressing any keypad key skips the wait.
  4. Once fully open, the pod stays open for SERVO_POD_OPEN_MS (10s). The
     window starts AFTER the raise completes, so the pod is genuinely open
     for the full 10s. Then the servo slowly lowers the sheet back DOWN over
     ~2.6s, holds LOCKED for SERVO_POD_SETTLE_MS (1s), and the signal is
     turned OFF - the servo goes limp and the sheet rests on its mechanical
     stop (no more 24/7 endstop grinding). Runs in the background regardless
     of the keypad screen.
  5. Wrong OTP, failed sequence, or 30s failsafe timeout -> pod never moves.

FAILSECURE (IMPORTANT - hardware)
---------------------------------
  - At boot the firmware snaps every servo to LOCKED (staggered, so the buck
    isn't hit by all servo inrush at once), then releases the signal idle so
    they go limp. A reboot can never leave a pod open.
  - Normally the pod servos are ASLEEP (signal off, no holding torque).
    The metal sheet MUST be designed so that whenever the servo is limp -
    idle, or when the power rail dies - it falls back DOWN (blocking the
    cash) by gravity or a spring. If your linkage holds the sheet UP without
    servo power, that would be fail-OPEN and a real cash-loss risk. Verify
    with the power-cycle bench test before deploying. (See CALIBRATION.)

CALIBRATION
-----------
  SERVO_PULSE_LOCKED_US / SERVO_PULSE_UNLOCKED_US in config.h control the
  endpoints (defaults 500us = ~0 deg and 2300us = ~170 deg). MG996R clones
  vary; tuning steps:
    a. Set UNLOCKED to something small (e.g. 600us), flash, unlock the vault
       fully once, and watch which direction the servo sweeps.
    b. Adjust UNLOCKED until the sheet is fully retracted (pod open).
    c. Adjust LOCKED until the sheet fully blocks the pod (pod closed).
    d. Re-flash with the tuned values. Never exceed ~2400us (endstop
       mechanical stress) or go below ~400us.
  NOTE - trim just inside the stops: the defaults sit AT the mechanical
  endstops (500us/2300us). If the sheet seals/opens fully a few degrees off
  the stop, prefer ~550-600us / ~2250us so the horns aren't jammed into the
  endstops. The servos normally sleep when idle, so this matters most during
  fire/re-lock and the boot snap.
  SERVO_RAMP_US_PER_SEC sets the sweep speed (default 700 = ~2.6s full
  travel). Raise for a faster "pull", lower for slower. Boot always snaps.


================================================================================
                        FEATURE FLAGS
================================================================================

In config.h, four flags control optional hardware:

  #define ENABLE_REED_SWITCHES  1    <-- active, reeds are wired
  #define ENABLE_IR_SENSORS     1    <-- active, IR sensors are wired
  #define ENABLE_SOLENOID_LOCKS 1    <-- active, relay + solenoids wired
  #define ENABLE_SERVO_LOCKS    1    <-- active, PCA9685 + MG996R wired

When OFF (0):
  - The GPIO pins are not initialized (no conflict if nothing is connected)
  - Boot self-test skips sensor/lock checks
  - The firmware runs with keypad + LCD + camera only
  - With locks off, a successful OTP only shows ACCESS GRANTED
  - With servo locks off, a confirmed delivery does NOT release the cash pod

When ON (1):
  - GPIO pins are set up as INPUT_PULLUP (reeds), INPUT (IR) and the relay
    pins as OUTPUT driven to the locked level at the very start of setup()
  - The PCA9685 is initialized on the I2C bus right after the LCD: all pod
    servos snap to LOCKED (staggered, so the buck isn't hit by all inrush
    at once), settle briefly, then the signal goes OFF (servos go limp, sheet
    rests locked by gravity - fail-secure at boot)
  - Boot self-test reads and prints sensor states + lock states
  - Door open/close and parcel present/empty events are monitored in the
    main loop; a successful OTP releases that vault's lock until the door
    closes again (or UNLOCK_MAX_TIMEOUT_MS elapses)
  - With a confirmed delivery (door_closed_locked) the cash pod servo
    slowly pulls the sheet UP (ramp at SERVO_RAMP_US_PER_SEC, ~2.6s),
    holds open for SERVO_POD_OPEN_MS (~10s), slowly lowers back, settles
    1s, then goes limp (no more endstop grind while idle)
  - If reed switches are disabled while locks are enabled, unlocking falls
    back to a fixed timed window (UNLOCK_FALLBACK_MS) since there is no
    way to detect the door closing (and the cash pod then never fires -
    a delivery can't be confirmed without door/parcel feedback)


================================================================================
                         BOOT SELF-TEST
================================================================================

On every power-up or reset, the keypad ESP32 runs this sequence:

  1. LCD splash screen ("LogiBox / Smart Vault v1.0") for 1.5 seconds
  2. If reed switches enabled: reads and prints door states
  3. If IR sensors enabled: reads and prints parcel states
  4. If solenoid locks enabled: prints lock states (always LOCKED at boot,
     no solenoid is ever actuated during the self-test)
  5. If servo locks enabled: prints cash pod states (snapped to LOCKED and
     released to idle in the init phase - no servo is re-moved during the
     self-test)
  6. Keypad check: shows "Press any key to continue..." (5s timeout)
  7. Increments boot counter in NVS (non-volatile storage)
  8. Shows "All OK - Boot #N" for 1 second
  9. Connects to WiFi (shows "Connecting WiFi" on LCD)
  10. Restores lockout state from NVS (if previously locked out)
  11. Enters the main vault selection screen


================================================================================
                       PARALLAX SCROLLING
================================================================================

When an LCD message exceeds 16 characters (e.g. error messages, lockout
timer), it automatically scrolls horizontally on both LCD lines.

  - Scroll speed: 300ms per character (SCROLL_SPEED_MS in config.h)
  - Pause at edges: 1000ms before scrolling starts/resumes (SCROLL_PAUSE_MS)
  - Applies to: OTP result messages, lockout countdown, status displays
  - Short messages (<=16 chars) display normally without scrolling


================================================================================
                    NVS PERSISTENCE (NON-VOLATILE STORAGE)
================================================================================

The ESP32's NVS (Preferences library) stores data that survives reboots
and re-flashes:

  - Lockout timer: if the device locks out from too many failed OTPs,
    the lockout expiry time is saved. On reboot, the lockout continues
    from where it left off.
  - Fail count: number of consecutive failed OTP attempts (resets on
    success or after lockout expires).
  - Boot count: incremented every boot (shown on LCD during self-test).

Namespace: "logibox"


================================================================================
                       WATCHDOG TIMER
================================================================================

A hardware watchdog timer (WDT) is configured for 15 seconds. If the
main loop hangs for more than 15 seconds, the ESP32 automatically resets.

  - Timeout: 15 seconds (WDT_TIMEOUT_SEC in config.h)
  - Set to 0 to disable
  - The watchdog is fed in the main loop() on every iteration
  - On reset, the full boot self-test sequence runs again


================================================================================
                    NON-BLOCKING ARCHITECTURE
================================================================================

All network work (camera commands, OTP verification) runs in a separate
FreeRTOS task pinned to core 0. The main loop (core 1) never blocks:

  - Keypad input stays responsive during HTTP calls
  - LCD updates happen immediately (no delay from network)
  - Camera start/stop commands don't freeze the keypad
  - OTP verification runs in background; result is queued back to main loop

Network requests go into a queue (max 4 pending). Results come back through
a separate queue and are processed on the main loop. Solenoid lock release
and re-lock timing are also handled on the main loop using the debounced
reed switch states - no blocking delays anywhere in the unlock flow.


================================================================================
                            TESTING
================================================================================

TEST 1: KEYPAD ALONE (NO SENSORS)
---------------------------------
  1. Flash the firmware with ENABLE_REED_SWITCHES=0, ENABLE_IR_SENSORS=0
  2. Open Serial Monitor @ 115200
  3. Boot sequence should complete (splash -> self-test -> WiFi -> ready)
  4. Press any key -> "Select Vault" -> pick vault 1/2/3
  5. Enter a 6-digit OTP -> "Verifying..." -> result displayed
  6. Press * to go back to vault selection

TEST 2: CAMERA ALONE
--------------------
  1. Power the ESP32-CAM on the same WiFi as the keypad
  2. Visit http://logiboxcam.local/start in a browser
  3. Open the web app -> Camera page -> "Captured Sessions"
  4. A session with new frames should appear every 3 seconds

TEST 3: KEYPAD + CAMERA (END-TO-END)
------------------------------------
  1. Power both ESP32s and make sure they are on the same WiFi
  2. Sign in to the web app as the device owner
  3. On the keypad, press any key -> "Select Vault" -> pick a vault (1/2/3)
  4. Enter the correct OTP -> "ACCESS GRANTED"
  5. The camera starts capturing and uploads frames tagged with that vault
  6. In the web app, Camera page shows the session; download a frame
  7. CAMERA AUTO-STOP: with the keypad, wait for IDLE_TIMEOUT_MS (15s) with no
     key presses (or press '*'). The LCD returns to the welcome screen and the
     camera is told to STOP - new frames stop appearing. NOTE: the camera keeps
     recording across SELECT_VAULT and retries; it only stops when the keypad
     returns to WELCOME (idle timeout or '*').

TEST 4: REED SWITCHES (NOW ACTIVE)
-----------------------------------
  1. Re-flash the keypad ESP32 (feature flag is already enabled)
  2. Boot self-test should print door states (CLOSED/OPENED for each vault)
  3. Open/close a vault door -> Serial prints the state change
  4. LCD shows door status updates

TEST 5: IR SENSORS (NOW ACTIVE)
-------------------------------
  1. Re-flash the keypad ESP32 (feature flag is already enabled)
  2. Boot self-test should print parcel states (PRESENT/EMPTY for each vault)
  3. Place/remove a parcel -> Serial prints the state change
  4. LCD shows parcel status updates
  5. PARCEL REMOVAL RE-ARM: unlock a vault, place a parcel, then REMOVE it and
     leave the beam empty for PARCEL_REMOVED_CONFIRM_MS (1.5s, config.h). The
     device sends a "parcel_removed" event, clears the parcel latch, and
     re-arms - the next delivery attempt starts clean. The lock re-engages
     only if the door closes while the vault is still empty (see TEST 6 step 9).
  6. Confirm the 1.5s confirm window: unlock again, place a parcel, then QUICKLY
     wave a hand through the beam (occupied-and-empty within 1.5s) and put the
     parcel back. The delivery must NOT abort - a sustained empty beam, not a
     brief blink, is what counts as a removal.

TEST 6: SOLENOID LOCKS (BENCH TEST - RELAYS ONLY, NO 12V)
----------------------------------------------------------
  1. Wire only the relay control side (IN1/2/3 + VCC + GND to the ESP32).
     Leave the solenoids and the 12V supply DISCONNECTED for now.
  2. Flash the firmware and open Serial Monitor @ 115200.
  3. Boot self-test should print "Vault N lock: LOCKED" x3 with NO relay
     clicking at any point during boot.
  4. Select a vault and enter a WRONG OTP -> no relay LED changes.
  5. Enter the CORRECT OTP -> after ACCESS GRANTED, the LCD shows
     "Vault N unlocked / Pull door open" and that channel's LED lights up.
     Serial prints "Vault N UNLOCKED".
  6. Trigger the reed switch (open then close the door or wave a magnet):
     when it reports CLOSED again, the LED turns off, Serial prints
     "Vault N RELOCKED" and the keypad returns to Select Vault.
7. Repeat step 5 but leave the door alone -> after ~30s the LED turns off
      by itself (failsafe timeout) and the LCD flashes "Auto-locked".
   8. Power-cycle mid-unlock -> relays drop immediately (fail-secure).
   9. DOOR-CLOSE PARCEL CHECK (the fast pull-out hole): repeat step 5, but this
      time pull the parcel OUT after it was detected and close the door quickly
      - even within the 1.5s removal window. The delivery must NOT confirm:
      Serial prints "no_parcel", the lock re-engages, and the cash pod NEVER
      fires. The beam is checked LIVE at door-close (parcelOk = parcel detected
      during the unlock AND still present now), so a fast pull-out-and-close
      can never drop cash on an empty vault.

TEST 7: SOLENOID LOCKS (FULL 12V)
---------------------------------
  Only after TEST 6 passes: connect the solenoids through the COM/NO
  terminals to the 12V supply and repeat steps 5-8. You should hear each
  solenoid click/retract on unlock and re-engage on door close.

TEST 8: CASH POD SERVOS (BENCH TEST - NO 12V YET)
--------------------------------------------------
  1. Wire the PCA9685 control side only (VCC 5V, GND, SDA 21, SCL 22).
     Leave the servo power rail (V+) and servos DISCONNECTED for now.
  2. Flash the firmware and open Serial Monitor @ 115200.
  3. Boot self-test should print "Vault N cash pod: LOCKED - asleep (ch N)"
     x3 (the servos snap to LOCKED, settle, then the signal goes OFF).
  4. Drive a full delivery to completion (correct OTP -> open door -> place
     parcel -> close door). Serial should print "Vault N CASH POD released
     (raising)" and the LCD should show "Releasing cash! / Vault N" for ~4s
     before returning to Select Vault (press any key to skip the wait).
  5. Over the next ~2.6s the servo ramps UP (watch the pulse in Serial), then
     "CASH POD open", holds ~10s, then "CASH POD lowering (auto re-lock)"
     ramps DOWN ~2.6s, and finally "CASH POD locked (servo asleep)" - all
     without touching the keypad. Verify the keypad/LCD stay fully responsive
     the whole time (the ramp is non-blocking).
  6. Run a failed/wrong sequence (wrong OTP, or open door -> close without
     a parcel): the pod must NEVER move.

TEST 9: CASH POD SERVOS (FULL 6V POWER)
---------------------------------------
  Only after TEST 8 passes:
  1. Set the buck converter output to 6V BEFORE connecting anything.
  2. Wire the three servos directly from the buck: all red wires -> buck +6V,
     all brown wires -> common GND. Orange signal wires -> ch 3/11/15 TOP pins
     on the PCA9685 (signal only - NOT the red/brown servo power pins).
     Verify ALL grounds (ESP32, buck, PCA9685, servos) are common.
  3. Repeat TEST 8 step 4: the correct vault's servo should SLOWLY pull the
     metal sheet UP (~2.6s wire-like motion), hold ~10s, then SLOWLY lower it
     back DOWN, settle 1s, and go limp/quiet (no hum while idle).
  4. Power-cycle MID-UNLOCK (kill the 6V rail while the pod is open): the
     servo goes limp. Verify your linkage falls back to the LOCKED position
     (fail-secure). If it stays UP, your cash pod is fail-OPEN - redesign
     the linkage before deploying.
  5. Confirm the idle behaviour: at rest the servos are asleep (signal off,
     no hum, ~no drive current). If they hum/grind while idle, the servo
     signal isn't being turned OFF - check the "locked (servo asleep)" log.
  6. Calibrate SERVO_PULSE_LOCKED_US / SERVO_PULSE_UNLOCKED_US (trim just
     inside the stops) and SERVO_RAMP_US_PER_SEC (sweep speed) as needed
     (see PART 4, CALIBRATION).


================================================================================
                         TROUBLESHOOTING
================================================================================

PROBLEM: ESP32-CAM won't enter download mode
SOLUTION:
  - GPIO0 must be held to GND BEFORE power is applied
  - Keep the jumper in place until the upload starts
  - Some USB-TTL adapters need EN grounded; try powering via 5V + EN to GND

PROBLEM: Keypad says OTP verified but no session appears in the app
SOLUTION:
  - Confirm both ESP32s are on the SAME 2.4GHz WiFi network
  - Check devices/esp32-cam-001 in Firestore has your ownerUid set
  - Test the camera alone first (TEST 2)

PROBLEM: No frames captured
SOLUTION:
  - Check the ESP32-CAM Serial Monitor for upload errors (HTTP code)
  - Verify FUNCTION_URL points to your deployed /api/camera-upload
  - Make sure both ESP32s joined the SAME network (set via the portal)

PROBLEM: Camera works but session label is missing/empty
SOLUTION:
  - Sessions started from the keypad include ?vault=N. Sessions started
    manually via /start have no vault and appear under "Unsorted".

PROBLEM: Keypad shows "Self-test... Check sensors"
SOLUTION:
  - A sensor is failing its boot check. Check Serial Monitor for which
    vault sensor reported an unexpected state. Verify wiring.

PROBLEM: Relay LED is ON when it should be off (inverted behavior)
SOLUTION:
  - Your relay board is active-HIGH. Set RELAY_ACTIVE_LOW to 0 in config.h
    and re-flash.

PROBLEM: OTP verified but no relay clicks / no solenoid movement
SOLUTION:
  - Check Serial Monitor for "Vault N UNLOCKED". If present, the firmware
    is fine: verify INx wire goes to the right GPIO, relay VCC is on 5V
    (VIN) not 3.3V, and relay GND is shared with the ESP32.
  - If missing entirely, ENABLE_SOLENOID_LOCKS may be 0 in config.h.

PROBLEM: Lock never re-engages after closing the door
SOLUTION:
  - The reed switch for that vault is not reporting CLOSED (check boot
    self-test output and door state prints). Verify reed wiring/alignment.
  - The 30s failsafe will still force a re-lock eventually.

PROBLEM: Solenoid hums but does not retract
SOLUTION:
  - Not enough current from the 12V supply or too thin wires. The 10A
    supply has plenty of headroom; check the solenoid's rated voltage and
    your wiring gauge/connections.

PROBLEM: Servo doesn't move but Serial shows "All cash pod servos: LOCKED"
---------------------------------------------------------------------------
  The boot log proves the code compiled and the PCA9685 answered on the bus.
  Isolate the fault in this order:

  Step 1: Confirm 0x40 on the bus (shared I2C with the LCD):
          If the LCD works but servos don't, the driver is NOT on the bus
          (LCD is 0x27, driver is 0x40 - no A0-A5 jumpers). Swap the dupont
          SDA/SCL at the module end if 0x40 doesn't show up. If it shows up
          at a different address, update PCA9685_ADDR in config.h to match.
  Step 2: Power. Confirm buck output = 6.0V and that the servo RED/BROWN wires
          are wired DIRECTLY from the buck (NOT through the PCA9685 header).
          This board's header power rows are not connected to the rail, so a
          servo plugged into the header gets NO power even with 6V on the V+
          screw. Verify with a multimeter directly on the servo red/brown pins.
  Step 3: Signal. Measure DC voltage on the servo ORANGE pin (or the header
          top pin) while the system runs:
            ~0.2V  -> pulses ARE present, problem is servo power (Step 2)
            0V     -> header not driving the signal; try moving the plug to
                      another channel (rules out a dead header pin)
          Confirm wire colors: orange signal, red +, brown GND.
  Step 4: Once power AND signal are both confirmed, re-flash LogiBox_OTP_Vault
          and run TEST 8 -> TEST 9.

PROBLEM: Cash pod never opens on a confirmed delivery
SOLUTION:
  - Check Serial for "Vault N CASH POD released". If missing, ENABLE_SERVO_LOCKS
    may be 0, or the delivery didn't reach the confirmed state (watch for
    "door_closed_locked" in the log; a "no_parcel"/"auto_locked" event never
    fires the pod by design - that is correct behaviour).
  - If released but the servo didn't move: verify PCA9685 VCC=5V, SDA=21/SCL=22,
    OE tied to GND, and that the servo signal wire is in the right channel
    header (ch 3/11/15 = vault 1/2/3) - and that the servo's red/brown power
    wires really are on the buck rail, not the PCA9685 header.
  - I2C conflict? The LCD must be at 0x27 and PCA9685 at 0x40 (no A0-A5
    jumpers). Both share GPIO 21/22.

PROBLEM: Servo moves the wrong direction / doesn't fully travel
SOLUTION:
  - Calibrate SERVO_PULSE_LOCKED_US and SERVO_PULSE_UNLOCKED_US in config.h
    (see PART 4, CALIBRATION). MG996R clones vary a lot.

PROBLEM: Pod servo twitches / jumps during boot
SOLUTION:
  - Servos are deliberately driven to LOCKED at startup - expect one rapid
    move to the locked position ASAP after power-on. If it only happens on
    every boot that is normal. If it happens repeatedly during normal
    operation, check the servo supply: add/keep the 2200uF capacitor and
    confirm the buck converter can deliver peak current.

PROBLEM: Cash pod opens on power loss (cash falls out)
RESULT:
  - This is a MECHANICAL fail-open design, not a software bug. The firmware
    drives LOCKED at boot and on the timed re-lock, but a dead servo has no
    holding torque. The sliding sheet MUST fall back down (locked) by
    gravity or a spring when the rail loses power. Redesign the linkage.
    (See PART 4, FAILSECURE.)


================================================================================
                         WIFI & NETWORK SETUP
================================================================================

No WiFi credentials are stored in the firmware. Each device is configured
ONCE via the WiFiManager captive portal - this is also how you move the
hardware to a different network later without editing or re-flashing code.

FIRST-TIME WIFI SETUP (per device)
----------------------------------
  1. Power the device. If it has no saved network it starts a portal hotspot:
       ESP32-CAM  -> AP name "LogiBoxCam"
       Keypad     -> AP name "LogiBoxKeypad" (LCD shows "Join WiFi: LogiBoxKeypad")
  2. From a phone, join that hotspot (no password).
  3. Open http://192.168.4.1 in the phone browser.
  4. Pick your WiFi network, enter its password, save.
  5. Device reboots and connects. Set up the other device the same way -
     BOTH must be on the SAME network so the keypad can reach the camera.

CHANGING NETWORKS LATER (e.g. deploying at a site)
--------------------------------------------------
  - The credentials are saved in NVS and survive re-flashes.
  - To change network: power-cycle the device while its current network is
    unavailable (or wait for it to fail to connect) - the portal AP restarts.
    Re-run the steps above. No code changes, no laptop needed.
  - ESP32-CAM shortcut: to force the portal even when the old network is still
    in range, power the camera on, then within ~5s HOLD the FLASH button
    (GPIO0) for 3 seconds and RELEASE it. The camera erases its saved WiFi and
    reopens the "LogiBoxCam" portal. The FLASH button is the GPIO0-to-GND
    button on the ESP32-CAM-MB programmer board. Do NOT hold GPIO0 during
    power-on - that enters download (flash) mode.

CAMERA DISCOVERY
----------------
  - The camera advertises the mDNS hostname "logiboxcam". The keypad resolves
    it automatically, so it works on ANY network (DHCP IP, no static config).
  - CAMERA_IP in the keypad code is only a fallback if mDNS fails; set it to
    your network's range if you ever need it (e.g. 192.168.100.151).
